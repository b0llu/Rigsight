Your PC went black, restarted, or threw you back to the desktop, and now you want to know why. Windows writes down almost every crash, it just doesn't show you. Here is how to find out why your PC crashed on Windows 11, and Windows 10 works the same way. Start with the quick view, then dig only as far as you need.

First, work out what kind of crash it was

"Crash" covers a few different things, and each one leaves a different trail. Before you open any tool, think about what you saw.

  • A blue screen with a stop code. On current Windows 11 it's a black screen that says your device ran into a problem, with the stop code in small text, and it only stays up for a couple of seconds. Windows itself crashed and saved a report.
  • The PC just went off or restarted with no blue screen. Windows had no time to write anything, so the record is thin.
  • One game or app closed and the rest of Windows kept running. That's an app crash, logged separately.
  • The screen went black for a few seconds and came back. That's a graphics driver reset, a different problem again.

If you didn't see it happen, the tools below will tell you which one it was.

Check Reliability Monitor

Reliability Monitor is the easiest place to start. It puts every crash of the last year on a calendar.

  1. Click Start and type reliability.
  2. Open View reliability history. You can also press Win+R and run perfmon /rel.
  3. Click the column for the day it crashed. Red X marks are critical events.
  4. Double-click an entry in the list below the graph to see the technical details.

What the entries mean:

  • "Windows was not properly shut down": Windows didn't get to shut down cleanly. On its own, that means the PC lost power, was switched off by holding the power button, or froze so hard that Windows wrote nothing. After a blue screen you see it too, next to the BlueScreen entry below.
  • "Shut down unexpectedly" with the problem name BlueScreen: a blue screen. The BCCode line is the stop code, such as 124 or 116.
  • "Stopped working" under an app's name: that app crashed. The details name the file it crashed in.

Read the crash logs in Event Viewer

Event Viewer has the same events with more detail, and exact times.

  1. Right-click Start and choose Event Viewer.
  2. Open Windows Logs > System.
  3. In the right pane, click Filter Current Log.
  4. In the box that says <All Event IDs>, type 41,1001,6008,1074 and click OK.

Now you only see the events that matter:

  • 41, Kernel-Power: "The system has rebooted without cleanly shutting down first." Windows writes it when the PC starts again. Click it and open the Details tab. If BugcheckCode is not 0, it was a blue screen. If it's 0, the PC lost power or was switched off. See our Kernel-Power 41 guide for every field.
  • 1001, BugCheck: "The computer has rebooted from a bugcheck." This one gives the stop code in hex and the path of the dump file Windows saved.
  • 6008, EventLog: "The previous system shutdown was unexpected." It gives the time Windows last knew it was running. That time can be stale by some minutes.
  • 1074, User32: a normal restart that a person or a program asked for. If you see one at the time of a "random" restart, it wasn't a crash. Windows Update is a common source.

For a game or app that closed, switch to Windows Logs > Application and filter for 1000 and 1002. Event 1000, Application Error, names the program, the faulting module and an exception code. Event 1002, Application Hang, is a program that froze and was closed. Our guide to games crashing to desktop goes through those fields.

Look for the minidump file

After a blue screen, Windows usually saves a small memory dump in C:\Windows\Minidump, one file per crash with the date in its name. Opening it takes a debugger. WinDbg is free from Microsoft. Open the file, run !analyze -v, and look for the line "Probably caused by". It often names a driver file such as nvlddmkm.sys.

You don't always need the dump: the stop code alone, from Reliability Monitor or Event Viewer, often says enough. If the Minidump folder is empty, open Settings > System > About > Advanced system settings, then Startup and Recovery > Settings, and set Write debugging information to Small memory dump or Automatic memory dump. The next blue screen will be saved. The small dumps go to the Minidump folder. The others are saved as C:\Windows\MEMORY.DMP.

What the evidence points to

Once you have the type and the code, the next step is usually clear.

  • A stop code that names a driver. Update or reinstall that driver. If the crashes began after a new driver, roll it back. Microsoft estimates that about three quarters of stop errors come from faulty drivers. Our blue screen guide lists the common codes.
  • Codes like 0x124 WHEA_UNCORRECTABLE_ERROR or 0x101 CLOCK_WATCHDOG_TIMEOUT. The hardware reported the error. Undo any overclock or undervolt, including XMP or EXPO memory profiles, and check temperatures.
  • Kernel-Power 41 with a code of 0. No blue screen was saved. Power is the usual suspect: the mains, the power supply, a held power button. Heat and unstable tuning can also do it. Our guide to random restarts walks through it.
  • The same app crashing in the same file. That program, a mod or an overlay is at fault, not the PC.
  • Different apps crashing at random, with different codes each time. That leans toward memory, the drive or heat. Run Windows Memory Diagnostic from Start and check your drive's health.

Also look at what changed. Reliability Monitor lists installs under Informational events, and Settings > Windows Update > Update history shows what Windows installed. A crash that began the day after a new driver arrived has a likely suspect.

The part Windows doesn't record

Windows logs the moment of the crash. It doesn't log what led up to it. Was the GPU at 90°? Was memory full? Was anyone even using the PC? For a sudden shut-off with no code, that's often the only real clue, and by the time you look it's gone.

That's why a monitor that records all day helps. You can't go back and measure a temperature from last Tuesday, but you can read one that was saved.

How RigSight does the digging for you

RigSight is a free, open-source Windows monitor. Its Crashes page reads the same Windows records you just looked at: blue screens, sudden shut-offs, app crashes and freezes, and graphics driver resets. It lists them on one timeline with the stop codes and file names already pulled out. When it first runs, it reads up to 90 days back from Windows' logs, as far as they still reach.

Every crash gets a plain sentence for the most likely cause and one word for how sure that is: Confirmed when Windows' own record says so, Likely, Possibly, or Not enough to say. A blue screen whose driver Windows named reads as Confirmed. A shut-off that neither Windows nor RigSight has anything on says Not enough to say, rather than guessing.

Open one and you also get what Windows can't give you. RigSight shows the 45 minutes before the crash and the 10 after: temperatures, load, power, memory, fans and the network, with the apps doing the work. It lists what it ruled out, such as "It wasn't overheating", and any driver, Windows update, BIOS or hardware change from the week before. Copy report puts it all in a block of text for a forum post, and the Event Viewer button opens Windows' own log. CPU temperature and power need RigSight running with admin rights. The readings only exist from when RigSight started recording, so older crashes from Windows' logs show without them.

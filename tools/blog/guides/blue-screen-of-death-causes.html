A blue screen with a sad face and "Your device ran into a problem", or on current Windows 11 a plain black screen with the same message that stays up for about two seconds. Then it restarts before you can read anything. The blue screen of death causes are fewer than they seem. A handful of driver and hardware problems make up most of them, and Windows tells you which one it was if you know where to look. This works the same on Windows 11 and Windows 10.

What a blue screen is

Microsoft calls it a stop error or bug check. Drivers and the core of Windows run with full access to the system. When one of them does something that could corrupt memory or your files if it carried on, Windows stops everything on purpose. It saves a dump file and shows a stop code that names the kind of fault.

Microsoft estimates that about three quarters of stop errors are caused by faulty drivers. In its own breakdown, hardware problems are about one in ten, and a share can't be traced at all because the memory was too damaged to read.

Find the stop code and the driver

The stop code is on the blue screen itself, such as Stop code: VIDEO_TDR_FAILURE, and sometimes a line saying What failed: nvlddmkm.sys. That second line is the driver Windows blames. If the PC restarts too fast to read it, turn off the automatic restart.

  1. Open Settings > System > About and click Advanced system settings.
  2. Under Startup and Recovery, click Settings.
  3. Clear Automatically restart under System failure, and check that Write debugging information isn't set to (none).

For crashes that already happened, you don't need any extra tool to get the code. Windows keeps it in two places.

  • In Reliability Monitor, type reliability into Start and open View reliability history. A blue screen shows as "Shut down unexpectedly" with the problem name BlueScreen. The BCCode line is the stop code in hex.
  • In Event Viewer, open Windows Logs > System and look for event 1001 from the source BugCheck. It reads "The computer has rebooted from a bugcheck" with the code, its four parameters and where the dump was saved. Kernel-Power 41 has the same code in decimal, and the Kernel-Power 41 post shows how to convert it.

To find the driver behind an old crash without WhoCrashed or other third-party tools, use Microsoft's own debugger.

  1. Install WinDbg. Microsoft offers it from its WinDbg download page and the Microsoft Store.
  2. Open it as administrator, choose File > Start debugging > Open dump file, and pick the newest file in C:\Windows\Minidump.
  3. Type !analyze -v and press Enter. Give it a minute to download symbols.
  4. Look for MODULE_NAME, IMAGE_NAME and the line "Probably caused by". A file ending in .sys is the driver. If it names ntoskrnl.exe, that's Windows itself, and the real cause is usually a driver or hardware further back.

Common stop codes and what they point to

  • 0x124 WHEA_UNCORRECTABLE_ERROR means the hardware reported an error it couldn't recover from. It's usually CPU or memory tuning, so undo overclocks, undervolts, Curve Optimizer and XMP or EXPO, and update the BIOS.
  • 0x101 CLOCK_WATCHDOG_TIMEOUT means a CPU core stopped responding. It's usually unstable CPU tuning.
  • 0x1A MEMORY_MANAGEMENT, 0x50 PAGE_FAULT_IN_NONPAGED_AREA, 0x4E PFN_LIST_CORRUPT point to memory. Test with XMP or EXPO turned off and run Windows Memory Diagnostic.
  • 0x116 VIDEO_TDR_FAILURE and 0x119 VIDEO_SCHEDULER_INTERNAL_ERROR point to the graphics driver. Clean-reinstall it and undo any GPU overclock.
  • 0xD1 DRIVER_IRQL_NOT_LESS_OR_EQUAL and 0xA IRQL_NOT_LESS_OR_EQUAL mean a driver touched memory it shouldn't. Network, audio and graphics drivers are frequent culprits.
  • 0x133 DPC_WATCHDOG_VIOLATION means a driver took too long. Often storage, chipset or network drivers, or SSD firmware.
  • 0x7A KERNEL_DATA_INPAGE_ERROR and 0x154 UNEXPECTED_STORE_EXCEPTION mean Windows couldn't read from the drive. Check the drive's health and its cable.
  • 0x9F DRIVER_POWER_STATE_FAILURE means a driver failed during sleep or wake. Update chipset and graphics drivers.
  • 0x3B SYSTEM_SERVICE_EXCEPTION, 0x7E SYSTEM_THREAD_EXCEPTION_NOT_HANDLED and 0x139 KERNEL_SECURITY_CHECK_FAILURE mean a driver crashed. Anti-cheat and recently installed software are common causes.
  • 0xEF CRITICAL_PROCESS_DIED means a core Windows process stopped. Run sfc /scannow and check the drive.

Microsoft's Bug Check Code Reference lists every code with its parameters, if yours isn't here.

Fixes, safest first

  1. Undo what changed last. For a new driver, open Device Manager, double-click the device, then Driver > Roll Back Driver. Take out new hardware and test without it. Uninstall new software, especially anything with its own driver.
  2. Install updates from Settings > Windows Update, then get the newest drivers for the device the stop code or WinDbg named, from its maker.
  3. Put all tuning back to default. Load BIOS defaults, turn off XMP or EXPO for a test, and reset GPU tools.
  4. Run Windows Memory Diagnostic from Start. Several memory codes in a row deserve a longer test with MemTest86.
  5. Repair Windows files by running sfc /scannow in Terminal (Admin). If it can't fix everything, run DISM /Online /Cleanup-Image /RestoreHealth followed by sfc /scannow again.
  6. Check the drive's health with its maker's tool, and keep 10 to 15% of it free, as Microsoft suggests.
  7. Check temperatures under load against your CPU and GPU maker's limit for your model.
  8. If Windows won't stay up long enough, start in Safe Mode. Go to Settings > System > Recovery > Advanced startup > Restart now, then Troubleshoot > Advanced options > Startup Settings > Restart and press 4. From there you can roll back drivers or use System Restore.

Updating the BIOS can fix 0x124 and 0x101 crashes on some boards, but a failed BIOS update can leave the PC unable to start. Only do it with your motherboard maker's instructions, on a stable PC, and never during a storm or on a laptop without its charger.

What RigSight records about a blue screen

RigSight is a free, open-source PC monitor for Windows. Every blue screen lands on its Crashes page with the stop code already named and explained, like "WHEA_UNCORRECTABLE_ERROR, 0x124", and what to try. When Windows names the driver at the next start, RigSight says it in plain words, such as "Windows crashed inside nvlddmkm.sys, the NVIDIA driver", and marks it Confirmed, because Windows' own record says so. A 0x124 or 0x101 with no driver named reads Likely a hardware fault.

Then it checks the things you'd otherwise check by hand. Was a driver or Windows update installed in the 7 days before? It names it, or rules it out when the same blue screen already happened before that update. Did the hardware hand over errors at the next start, or did a drive log errors in the half hour before? Was the CPU or GPU over your alert limit? It also says how many times the same blue screen has happened before, and since when. Open the crash for the 45 minutes before it, minute by minute, and use Copy report to paste the whole thing into a forum post. CPU temperature and power need RigSight running with admin rights.

Your next step is to find the BCCode of your last blue screen in Reliability Monitor and match it against the list above. If your last few crashes all have the same code, fix that one thing first. If they're all different, start with memory and tuning.
